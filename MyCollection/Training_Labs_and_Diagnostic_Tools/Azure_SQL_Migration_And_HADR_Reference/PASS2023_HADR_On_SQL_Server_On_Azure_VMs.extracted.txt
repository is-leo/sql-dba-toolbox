Disaster Recovery solution, not really viable for High Availability
Databases backed up to Blob storage in a different datacenter for DR
Backup Options:
Manually take backups
Automated Backups via the SQL IaaS Extension on Azure VM
Azure Backup for Enterprise software experience

## ppt/slides/slide13.xml
Log Shipping
Backup transaction logs on primary
Jobs are used to copy and restore to secondary SQL Server
Good for disaster recovery
Can be used for High Availability, but the secondary would be unavailable during restores
Manual failover
Straightforward to implement

## ppt/slides/slide14.xml
Failover Cluster Instance
Instance is protected not just database
Jobs, linked servers, etc.
Requires shared storage for all nodes
A single point of failure unless replicated
No readable secondary
Only one copy of the data
Need to use log shipping, replication, or some other method to read the data not from the primary
Failover == everything moves nodes
Don't need Enterprise Edition

## ppt/slides/slide15.xml
Failover Cluster Instance – Storage Options
Azure Shared Disks
A feature of Azure Managed Disks
Use either Premium SSD or Ultra Disks
Supports all versions of SQL Server
Premium File Shares
A feature of Azure files
SSD backed and have consistently low latency
Supports SQL Server 2012 and later
Storage Spaces Direct (S2D)
A software based virtual SAN
Can only be used in an availability set
Supports SQL Server 2016 and later
Limitations with each option should be reviewed when setting up an FCI

## ppt/slides/slide16.xml
Always On Availability Group
Available in Standard and Enterprise editions
Standard Edition has fewer features including only one database per AG, two replicas per AG, and no read-access to the secondary
AGs are done at the database level not instance level
Except in SQL Server 2022 where Contained AGs can copy logins to replicas
Up to nine replicas including readable secondaries with Enterprise Edition
Manual or Automatic Failover
Listener can be used to connect to the database without knowing the instance

## ppt/slides/slide17.xml
Always On Availability Group – Listener Options
Multi-subnet configuration matches on-premises
Uses multiple subnets in the same virtual network
Single subnet configuration
Virtual Network Name (VNN) listener and a load balancer
More complexity and increased maintenance
Increased failover time due to load balancer
Distributed Network Name (DNN) listener
Must use a unique port
Some restrictions on what versions of SQL Server are supported

## ppt/slides/slide24.xml
Scenario Overview
Contoso Corporation is a multinational business with its headquarters in Boston and operations across the globe. They are creating a division to build new products and need SQL Servers to support the backend. They are in the planning stages and have outlined requirements for the initial launch. Your job is to propose the HA/DR solution for each of them.

## ppt/slides/slide25.xml
Scenario 1
Contoso Corp. wants a development/test environment that will be periodically refreshed with new data for accurate testing.
Key Requirements:
Not customer facing (internal only)
Can be down for 1-2 days, if needed, due to disaster
Node resiliency not needed
Refreshed weekly
Only used Monday – Friday (9am – 5pm)
What do you propose?
Backup and Restore
But if refresh rate is more frequent, then possibly log shipping

## ppt/slides/slide26.xml
Scenario 1 – Best Practices in Azure
Things to Consider:
A storage account is needed
Performance implications of backup
Timings and size of the backup
Size of the VM selected – network throughput (bandwidth) and IO throughput
Where backups are placed – local storage, Blob storage
Enable backup compression

## ppt/slides/slide27.xml
Scenario 2
Contoso Corp wants reporting on a few key databases for internal teams who shouldn't have access to production SQL Servers.
Key Requirements:
Internal team use
Access to < 10 databases is needed
Can be down for up to 2 hours, if needed, due to disaster
Does not need to be real-time data, delays of up to 30 minutes is acceptable for these reports
What do you propose?
Log Shipping

Scenario 3
Contoso Corp. has pivoted and added a new requirement to one of the projects. They are creating a multi-tenant application and each customer will have its own database for security reasons.
Key Requirements:
Application with high throughput (heavy transactions)
High transaction log generation rate
More than 100 databases that have to failover together

## ppt/slides/slide31.xml
Scenario 4
Contoso Corp wants to offload the read-heavy processes to another server. They expect that this will be needed across 75 databases. Additionally, they want the data to be as real-time as possible.
Key Requirements:
< 100 databases
Readable secondary with near real-time data
~5 minutes of downtime allowed on main SQL Server
Regional replica for DR may be required in the future
What do you propose?
Always On Availability Group with automatic failover
